# Read-only UI history audit

Use this for a monthly reconciliation when balance changes can make `purchased − balance` wrong.

## Per client

1. In the authenticated Yclients client base, search by email and open the exact client link (not the table row checkbox/container).
2. Open **Лояльность**. Before concluding that there are no cards, enable **«Показать все абонементы и сертификаты, включая просроченные и исчерпанные»** (`[data-locator=all_abonements_visibility]`) and wait for `[data-locator^=abonement_container_]` to reload. For every relevant card, open **История**.
3. Record only rows whose operation is `Списание`. Ignore `Продажа` and every `Изменение баланса`.
4. Group attendance = sum of actual group write-offs (normally 1 ₽ each).
5. Individual attendance = sum of all actual individual write-off amounts, rounded only after summing: `1 ₽ = 1 consultation`. Do not assume a fixed pair: component amounts may be `0.08 + 0.92`, `0.05 + 0.95`, or another split.
6. Open **История посещений** and count rows paid by `Абонемент` with `1 визит`, separately for group and individual services.
7. Stage the proposed `Отходили` values in an audit artifact first. Apply them to the report only after the complete month passes card-selection, reconciliation, and global sanity checks. Leave disagreements as explicit exceptions; never repair them with `purchased − current balance`.
8. Current balance remains the source for `Осталось`; an admin balance change may alter remaining balance but never attendance or overdue.
9. Before writing, inspect at least one known-positive client whose detailed history contains a real `Списание` and verify that the parser returns the expected non-zero count. A month collapsing to zero or near-zero attendance is a stop signal, not a plausible result to publish without manual validation.
10. Apply verified changes atomically or from a reversible snapshot. Never progressively zero rows during exploratory batches; batches should persist evidence, not mutate the production sheet.

## Card selection

- Match cards to the sale using product kind, creation/sale date, purchased quantity, and sale-history evidence—not only the nearest date.
- If several same-kind cards are equally plausible (especially several cards created on the same day), do not pick one arbitrarily and do not sum all cards blindly. Preserve all candidates and flag the row until the exact sold card(s) can be identified.
- Require detailed history to be non-empty and to belong to the selected card container. A successfully loaded client modal or an empty visit table is not proof that a card has zero consumption.

## UI automation notes

- Client-card UI has shown detailed transaction rows under each card's `История`; parsing only the compact card summary is insufficient for this audit.
- In the UI DOM, reliable targets observed: `li.client_loyalty_cards_tab`, `[data-locator^=history_panel_button_]`, `[data-locator=td_history]`, `li.visit_history_tab`, and `tr.erp-client-visit-history-table-visit-item-row`.
- **Do not read history immediately after clicking its panel button.** Expansion/loading is asynchronous and an immediate DOM read can return an empty `td_history`, falsely turning real write-offs into zero. Wait until the selected card's history contains the transaction header plus dated rows (or until a bounded timeout), then parse. For bulk clicks, verify every selected relevant card independently rather than sleeping once and assuming all panels loaded.
- Visit-history labels contain variable tabs, spaces, and line breaks. Never match the literal string `Абонемент\n1 визит`; normalize whitespace or use a Unicode-aware expression equivalent to `Абонемент\s*1\s*визит`. Verify this against a known-positive client before accepting a batch.
- Split transaction history by dated operation rows. Count only rows whose operation field is exactly `Списание`; then sum all ₽ amounts within that row. Exclude `Продажа` and `Изменение баланса` before summing. For individual cards, round/validate only the final summed amount, not each fragment.
- In browser-native `document.querySelectorAll`, do **not** use jQuery-only selectors such as `[data-locator!=abonement_container]`. They raise a DOM selector error; if the automation wrapper suppresses JavaScript exceptions, this can silently become an empty card list and zero every history count. The specific-card locator already has a safe discriminator: use `[data-locator^="abonement_container_"]`, because the generic container has no trailing underscore. Treat a null/empty extracted card array as an extraction failure, never as zero attendance. Surface `Runtime.evaluate.exceptionDetails` instead of coercing failed evaluations to `[]`.
- Client-base search is debounced. Wait for the exact email result before opening its edit-client link; do not reuse the previous result. Select the nested `*_edit_client_link_*` anchor, not the table-row container or checkbox; the anchor text often has only the client name, so match the email against its **parent/enclosing row**, not `closest('[data-locator^=client_tr_]')` on the anchor itself (the anchor's own locator also starts with `client_tr_`). If an exact email yields multiple rows, search the source’s normalized full phone and require exactly one client ID that is present in the email candidate set. Persist the email and phone candidate lists; never resolve a duplicate email by first-result order.
- If the sales-export email finds no client, retry by normalized phone and exact Telegram username from the export. Yclients may contain a typo or a different email while the display name still embeds the same Telegram username. Persist the resolved alias for later runs; do not silently substitute a merely similar client.
- After opening **Лояльность**, the default UI may show `У данного клиента нет карт` while expired/depleted cards are hidden. Click `[data-locator=all_abonements_visibility]`, wait for the reload, and only then classify card availability. Require both a selected relevant card and loaded detailed-history text before accepting a zero/zero reconciliation.
- Card metadata labels in `innerText` may appear **after** their values (for example `12.08.2025\nДата создания` and `08.06.2027\nСрок действия`). Do not parse dates with a one-sided `Дата создания\s+DATE` regex. Prefer the dedicated DOM locators `[data-locator=abonement_creation_date]`, `[data-locator=abonement_expiration_date]`, and `[data-locator=abonement_status]`; only use text fallback patterns that support both label orders. Parse visible balances from `[data-locator^=abonement_united_balance_service_count_]` / `[data-locator^=abonement_balance_service_count_]`, then validate against the `Общий баланс` text.
- Bootstrap client modals remain in the DOM while fading out. Before searching the next client, click the visible `.modal.in .close`, wait until `.modal.in` is absent, and then wait for `[data-locator=search_input]` to reappear. Otherwise a new result click can be routed into the stale client card and produce an empty modal.
- A browser/profile restart can preserve enough cookies to display the client base while loyalty-card requests still return HTTP 403. Treat `client base works + loyalty endpoint 403/empty modal` as expired authorization, not as «абонемента нет». Also treat an HTTP 200 JSON wrapper such as `{"success":false,"data":null,"meta":{"message":"Недостаточно прав","status_code":403}}` as a **logical 403**: transport status 200 does not make the response usable. Retry transient `200 + success:false` responses only to a strict cap; if the logical 403 persists on a fresh target and a repeated known-positive preflight, stop and require reauthentication rather than increasing the cap or accepting empty cards. When repeated transport-200 `success:false` bursts are transient rather than logical 403, keep the cap fixed and add bounded pacing between the preflight and clients (and between clients), then rerun the entire affected offset. Do not mix a failed fast-paced partial offset with a later paced retry.
- For remote reauthentication, use a short-lived visible browser attached to the same profile and expose it only through a localhost-bound VNC/websocket service plus an HTTPS tunnel protected by a freshly generated high-entropy VNC password. The user enters YCLIENTS credentials and 2FA directly in that browser—never in chat. As soon as they confirm completion, terminate the public tunnel, websocket proxy, and VNC server; delete temporary password/auth files; keep only the authenticated browser session alive; then prove the known-positive all-status endpoint before resuming. Verify the VNC/websocket ports are closed before continuing. After the monthly audit and final readback finish, terminate the authenticated browser/CDP session too and verify that no process still uses the dedicated profile. Do not report the public URL or temporary password in durable artifacts.
- A known-positive 200 preflight is necessary but not sufficient: authorization can fail again partway through a batch, and one affected client may briefly return 200 while the next request—or a repeated preflight—returns 403. Do not combine those mixed results into a valid checkpoint.
- Run a long monthly audit in small restartable batches. Persist each batch's verified records and exception list before starting the next batch. Accept a checkpoint offset only when every expected row in that offset completed under the same parser generation with all-status/history success and zero write-like requests. A checkpoint file written incrementally and interrupted after only part of its expected rows is incomplete even when every stored row has `ok=true`; preserve it only as forensic evidence and rerun that offset from its beginning. If any row returns a transport or logical 403, invalidate the whole affected offset, preserve earlier fully successful offsets, and rerun that offset from its beginning only after a fresh verified-ready session is stable. A new CDP target that reuses the same cookies is merely a diagnostic retry; recurring 403 there requires reauthentication and a blocker report, with Sheet and sequential ledger unchanged. If the remote-debug session becomes unresponsive without an auth failure, first try a fresh authenticated client-base tab; if a browser restart is required, re-verify loyalty authorization before resuming. Do not rerun or overwrite already verified offsets.
