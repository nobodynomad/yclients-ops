# Yclients Subscription Reporting

Use this skill when a user needs an online reporting table that combines a sales/export CSV with Yclients clients, subscriptions, records, and visit history.

## UI audit automation pitfalls

When auditing expired or exhausted subscriptions through the Yclients client-card UI:

1. After opening `Лояльность`, enable `[data-locator=all_abonements_visibility]`; otherwise expired/exhausted cards are silently omitted.
2. Card containers use `[data-locator^=abonement_container_]`. Do not use the invalid CSS selector `[data-locator!=abonement_container]` with `querySelectorAll`.
3. After clicking `[data-locator^=history_panel_button_]`, wait for the history DOM to render before reading `[data-locator=td_history]`.
4. Visit rows contain variable whitespace/tabs. Detect `Абонемент ... 1 визит` with `r'Абонемент\s*1\s*визит'`, not an exact newline string.
5. For individual/package cards, sum all actual `Списание` amounts and round only the card total: 1 ₽ = 1 consultation. Exclude every `Изменение баланса` from attendance/overdue, but parse its `(xOLD) → (xNEW)` transition separately for the manual-adjustment columns and effective quantity.
6. Package rows (`Пакет консультаций 3/5/8`) store `Отходили` in column G, unlike main rows where group/individual attendance are H/I.
7. In client-base search results, both the row DIV and its child edit link can have `data-locator` beginning with `client_tr_`. For exact email/alias validation, inspect `link.closest('div[data-locator^=client_tr_]')`, not generic `closest('[data-locator^=client_tr_]')`, and never take the first visible result before the exact row text changes—doing so can silently audit the previous client. If an exact email returns multiple client rows, re-search by the source’s normalized full phone and require a unique client-ID intersection with the email candidates; persist both searches as identity evidence rather than choosing the first duplicate-email row.
8. After Chrome/browser restart, the client list can still render while loyalty-card requests return HTTP 403 and empty modals. Every read-only request to `/loyalty_cards/get_client_loyalty_cards_json/...` must include `X-Requested-With: XMLHttpRequest`, matching the YCLIENTS frontend. Without that header, the exact same URL can return HTTP 403 `text/html` across any `x-bounce-id`; with the header it returns HTTP 200 `application/json`. Treat such a headerless 403 as an audit-harness defect: invalidate the affected checkpoint and rerun it after fixing the request. Instrument and persist `status`, payload `success`, `content-type`, and `x-bounce-id` for every attempt. A correctly headed request can also transiently return HTTP 200 JSON with `success:false`, `data:null`, and no card HTML; retry that exact response with a strict cap, and accept only `success:true` with complete card HTML/histories. If its JSON `meta.status_code` is `403` or the message says `Недостаточно прав`, classify it as a **logical 403** despite transport HTTP 200. After the strict cap and one fresh-target known-positive preflight, require user reauthentication instead of accepting empty cards or extending retries. After fixing the header or reauthenticating, verify a known loyalty-card request returns usable `success:true` data before resuming batches. If a correctly headed transport/logical 403 recurs on the known-positive preflight, stop without Sheet/ledger changes. Preserve only earlier fully successful offsets; an incrementally written partial offset is incomplete even when every stored row says `ok=true`, so rerun that offset from its beginning. For remote reauthentication, use a short-lived password-protected visible-browser tunnel; the user enters credentials directly there, and the tunnel/VNC/websocket layers plus temporary auth files are removed immediately after confirmation while the authenticated browser stays alive. See `references/ui-history-audit.md` for the secure reauthentication and checkpoint procedure.
9. The visit-history tab is lazy-loaded. On a fresh browser, calling `initializeModule()` and `openTab()` in one immediate expression can emit the client before the module listener exists, producing visit status `0`. Call `initializeModule()`, wait for `window.vue.ErpClientsTabs`, then open `client_visit_history`, wait for `.erp-client-visit-history-tab-content`, allow a short stabilization delay, and only then emit the client. A status-0 visit response invalidates the affected checkpoint; rerun it completely after fixing initialization. For any newly opened CDP target, also verify both the known all-status endpoint and the actual client-base UI: HTTP 200 is insufficient if `[data-locator=search_input]` never appears. Close stale unused YCLIENTS targets before opening more; if a target fails readiness, discard only that target and retry the remaining checkpoint offsets in a verified-ready tab. Never record `search input missing` as a client result.
10. When a source sale has a blank email and is matched through Telegram, do not add `"": username` to the alias map without also requiring a non-empty course/source marker while reading sheet rows. Otherwise every blank analytics/separator row is misclassified as another client. If a captured monthly skeleton has an email but the mutable source later blanks that email, permit the current-source match only through an explicit mapping from that captured email to the exact normalized Telegram username, with the exact course and stable per-sale identity still required; do not treat blank email itself as a candidate key. The same explicit alias rule applies when the mutable source replaces the captured email with a different nonblank email: accept only the exact allowlisted alternate email (or exact allowlisted Telegram username), plus matching course/quantities and a unique source row; never use a broad alias substring or first-candidate fallback. If the mutable source contains multiple real blank-email rows with the same course and quantities, require the captured exact Telegram username or normalized phone too, and pin any accepted date drift in the manifest; never take the first match. Preserve exactly one source row per sale, then fill email only if the matched YCLIENTS card actually provides one.
11. When extracting a phone from a client-base result row, parse the dedicated displayed phone line (normally the line beginning with `+`) and enforce 8–15 normalized digits. Do not run one whitespace-spanning phone regex over the whole row: it can concatenate the phone with a numeric email local-part and make read-only visit-history searches fail validation.
12. Split detailed-history operations only at a line-start date immediately followed by an `HH:MM:SS` timestamp (on the same DOMParser line or the next live-modal line). Dates embedded in an `Изменение даты окончания` payload have no following timestamp; treating them as operation starts truncates the real history block and creates fake empty operations.
13. Before any Sheets mutation, bind the destination by spreadsheet ID + tab title + exact `sheetId`, and bind any formatting template by title + exact `sheetId`; reject a mismatch before building requests.
14. Treat source-derived text as literal `stringValue`, even when it begins with `=`. Carry report formulas as typed formula objects and allow `formulaValue` only at a fixed coordinate allowlist. Pick one coordinate convention for that allowlist and document it explicitly. If a serializer accepts zero-based `(row, col)` but its allowlist helper uses one-based sheet rows, test both the helper directly and the serializer path (`row_index + 1`); otherwise totals and analytics formulas can be silently written as literal strings through an off-by-one error.
15. When inserting a row, read, virtualize, clear, and verify at least one extra tail row so the former last checked row cannot shift beyond verification. Verify blank separator/report-tail notes as well as values.
16. Apply or normalize conditional-format rules after structural insertion/copy-format operations, in a separate batch when necessary; Google Sheets can discard a rule added in the same batch as an `insertDimension` affecting its range. Require a final zero-write rerun.
17. If the live operational source is a mutable client snapshot rather than an immutable sale ledger, bind stable sale identities to the captured month skeleton, independently re-prove current email/course/quantities, record a digest manifest for every checkpoint, and pin any current-source date drift explicitly. A pinned current date may move outside the captured month, so the current snapshot’s raw month count can be lower than the stable skeleton count; do not drop or re-bucket that sale when contact/course/quantity identity is still uniquely proven. Record the exact stable date and exact current date per source row in the manifest and regression test.
18. When adding an analytics row only to shift an existing package block and the sheet already has sufficient grid rows, prefer a complete scoped A:Q target rewrite over `insertDimension`. This avoids displacing an unchecked tail row. Enforce the final note set exactly so evidence notes move with their stable source rows and stale notes are cleared.
19. Build yellow `Обнулен` and red `Абонемента нет` fill requests from the computed exception-row lists. Never hard-code one exemplar row: a later ordinary-format copy can otherwise turn the remaining exception rows white or partially filled.
20. When cloning a monthly audit harness, re-derive the Google Sheets source-read range from the new month’s **last semantic source row**, including the lower consultation-package block. A copied fixed range can cover every main row while silently omitting package rows located below analytics/separators. Before any YCLIENTS audit, assert that the range end is at or beyond `max(expected source rows)`, then require the stable skeleton to contain the exact ordered main-plus-package row coordinates. Add a regression test for this coverage; do not infer completeness merely from a successful Sheets API response or from the main-block count.
21. If the live monthly tab has already lost or shifted a source sale during an earlier rewrite, do not accept that corrupted tab as the stable skeleton and do not reduce the source count to make it fit. Recover the original ordered sale identities from immutable, complete historical checkpoints (or another provenance-locked capture), assert exact main/package coordinates and uniqueness, and independently re-prove every recovered identity against the current sales source. Record the target-row loss as reconciliation evidence, regression-test the recovered identity, and let the final scoped full-target rewrite restore the missing row before advancing the ledger.
22. If the month being corrected is also the formatting-template sheet (`target sheetId == template sheetId`), a broad target fill reset can mutate the copyPaste source before later requests run in the same batch. Do not assume same-batch copyPaste reads a pre-batch snapshot. Add a regression test for this exact identity case, and restore semantic fills/styles with explicit final formatting requests (or snapshot source formats before mutation) after all broad clears and ordinary style copies. Verify the failed attempt’s partial write through a fresh read, repair it before continuing, and require the normal final zero-write rerun before ledger advancement.
23. When a previously corrected monthly tab is reused as the formatting template for later months, re-inspect its **current semantic row coordinates** before building copyPaste requests. A prior analytics-row insertion or full-target rewrite may have shifted the package title/header/data/total/rate rows while leaving an older executor’s absolute template indices stale. Regression-test every semantic source interval against the live template (`title`, `header`, ordinary package row, package total, package rate) and never inherit pre-rewrite absolute indices merely because the template sheet ID is unchanged.
24. The authenticated client-base route is `https://yclients.com/clients/{company_id}/base/`; the older shorthand `/client-base/{company_id}` can now return a real 404 page even with valid authentication. Require both the `Клиентская база` title and `[data-locator=search_input]` before auditing. For a known-positive all-status preflight, do not blindly select the first monthly source row when that row is an approved verified no-subscription exception; choose the first source outside the approved no-subscription set and regression-test that selection.
25. A semantically ordinary template row must also be verified as visually ordinary before using it as the repeated formatting source. The first data row of a completed month may be a red `Абонемента нет` exception or yellow `Обнулен` row even though its coordinates look convenient. Inspect its full A:Q fill/style (and the source cell used for repeated manual columns), select a proven white ordinary row instead, and regression-test both the exact source interval and the absence of exception fill. If final readback catches a bad template fill after an atomic write, treat that as a partial apply: do not advance the ledger, add the failing regression, rerun a complete scoped formatting repair, verify all cells again, and only then require a zero-write rerun.
26. Keep **candidate no-subscription rows** in the audit harness separate from the **freshly verified no-subscription set** in the manifest/reconciliation. A historically empty row can acquire a card later. The harness may still need row-specific permission to accept an empty fresh result, but the manifest must derive its final exception set only from current `no_subscription=true`, zero-card, exact-search evidence. Never force a newly appearing card back to zero merely to preserve historical expectations.
27. Fail closed on multiple selected cards in one family, but allow an exact row-specific aggregation when a newer card is proven to be an operational adjustment companion (for example, created with a standard balance and immediately reduced to a small aligned balance). Do not globally relax the tie gate. Regression-test the allowlisted row and selected locators. Exact card/course semantics can also require excluding a same-day wrong-size package card even when nearest-date matching would retain it. See `references/fresh-audit-drift-and-multi-card-adjudication.md` for the evidence patterns and gates.

## Core workflow

1. **Inspect the target table before designing anything.** Preserve its exact sheet-per-month layout, header names, header order, and absence/presence of extra columns. Do not add “helpful” columns without explicit approval.
2. **Parse exports safely.** Detect delimiter and encoding; Russian CRM exports may be UTF-8 BOM with semicolon delimiters even when named `.csv`. Store `Дата покупки` as a date-only value (`dd.MM.yyyy`) in both the main and consultation-package blocks; strip the time component from the underlying spreadsheet value, not only its display format. Treat local chat/cache copies as disposable: if the export is missing locally, recover the newest plausible consolidated-sales snapshot from the user-authorized Google Drive, then verify its schema and requested-month row counts before using it.
3. **Agree on reconciliation rules before bulk work.** Confirm:
   - month bucketing source (usually purchase date);
   - client match priority (email first, then normalized phone; flag ambiguous matches);
   - which subscription names/services count as group vs. individual;
   - the authoritative subscription expiry field;
   - what represents an attendance;
   - how overdue balances are calculated.
   - If the user is sending rules in several messages and says to wait for «готово», acknowledge receipt briefly and do not analyze, change scope, or start processing until they send it.
4. **Use least-privilege Yclients API access.** Read-only permissions should cover clients, client history, services, records/journal, subscriptions, and subscription history. Never request write/delete rights for reporting.
5. **Do a 10–20 row sample first.** Show unmatched, duplicate-match, and unexpected-service cases before processing the full export.
6. **Write monthly tabs only after rules are approved.** Preserve manual values/comments where required; keep a separate exception list only if the user approves an additional sheet.
7. **Split structurally distinct course families when the approved template does.** For consultation-only packages (for example exact course names `Пакет консультаций 3`, `Пакет консультаций 5`, `Пакет консультаций 8`), remove them from the main group/individual block and place them in a lower section with only `Инди`, `Отходили`, `Осталось`, and `Просрочилось` columns plus its own `Итого`. When mapping consultation-package quantity, the explicit course mapping is authoritative: `Пакет консультаций 3/5/8` maps to fixed quantities `3/5/8`, regardless of a contradictory technical `userCourse.kolPersonalConsultations` value (for example, a `Пакет консультаций 3` sale can carry raw personal quantity `1` while the approved target is 3). Require the exact package course and reject conflicting group quantity; do not substitute raw ordinary-course fields for the mapped package quantity. Some exports put an explicit package count in the group field; never overwrite that count by parsing `3/5/8` from the course title for non-package courses. Package validity comes from the live package subscription type; do not apply ordinary-course grace-period logic. If the package course is unknown or its mapping is missing, stop rather than infer a quantity.
8. **Preserve the template’s final total row when present.** If the approved example ends with `Итого`, append it after the last data row and sum the numerical consultation columns (typically group, individual, attended, remaining, and overdue). Use spreadsheet formulas; text `-` cells for expired current balances must not be counted.
9. **Add rate and unrealized rows only when requested or present in the approved template.** Place rate rows left-aligned below their section total. Calculate each rate against that section’s effective purchased total (attendance, remaining, overdue), format as percentages, and use formulas rather than hard-coded values. In the main block, show `Нереализованные консультации` as two separate rows—`групп` and `инди`—using `effective total − overdue − attended` for each type. Then add `Клиенты без посещений` with a dynamic count of clients whose group and individual attendance are both zero, excluding `Абонемента нет` and `Обнулен`; require it to equal the approved red-font row count. Leave two blank rows after these analytics before the `пакет конс` heading. Give the consultation-package block its own individual-only rates, but do not add main-block manual-adjustment columns there. If the month has zero package sales, keep the approved empty package header and zero `Итого` row, and write numeric `0` rate values formatted as percentages; do not emit division formulas or locale-sensitive `IFERROR` formulas for the empty denominator. Derive all total and rate row numbers after partitioning data; never hard-code them because monthly row counts differ.
10. **Verify totals and formulas.** Re-read the written Google Sheet, compare main-plus-package row count to source, validate allowed status values, and explicitly scan rendered cells for formula errors such as `#DIV/0!` or `#ERROR!`. Reconcile each section by type: `effective quantity = attended + remaining + overdue`; when an ordinary main row legitimately differs because of the approved effective-quantity rule, expose it through `Нереализованные`, but do not leave an unexplained gap in the package block, which has no unrealized row. Report source-only / unmatched Yclients fallbacks separately.
11. **Remap formatting by semantic row, never by inherited absolute position.** When a new month has a different row count, duplicated gray/green fills remain at the old month’s row numbers. Clear displaced fills from the report tail, then apply gray only to the actual `Итого` rows and green only to the actual package header; ordinary rows and statuses stay white unless the user-approved yellow/red exception rules apply. Use the unchanged template sheet as the format source so an earlier copy operation cannot overwrite a style that a later operation still needs. For newly added manual-adjustment columns, never copy a long template-column range that includes the template’s old gray total row: copy the header style once and repeat one ordinary data-row style across the current data rows, then format the real total separately. Verify empty rows below the report and every ordinary data row across all columns have no residual fill.
12. **Use one writer and provenance-locked checkpoints.** Reviewers and delegated analyzers must operate on immutable snapshots without Sheet/ledger write capability; a read-only prompt is not access control. Before apply, require every possible writer to be finished, re-read executable hashes, target Sheet, ledger, checkpoint manifest, and dry-run, and reject any drift. Stamp checkpoints with parser/audit version and hash so batches from different parser generations cannot be consolidated. Treat local checkpoint, manifest, and executable-script writes as writer activity even when YCLIENTS access itself is read-only. A marker file is not serialization unless every cron, interactive, and helper entrypoint acquires and holds the same OS-level lock for the full run. If an overlapping interactive session exists because the user explicitly requested the same month there, the scheduled run must yield: identify the owner before terminating unfamiliar processes, do not publish or advance the ledger, and let the interactive run continue. If all-status auth becomes HTTP 403 or any unexpected concurrent write is detected, quarantine misleading success artifacts, restore the proven pre-apply state, keep the ledger on the same month, and stop. Follow `references/google-sheets-mutation-review.md` and `references/sequential-multi-month-reconciliation.md` for the full recovery, arbitration, and single-writer gates.

## Sequential multi-month execution

When the user asks to correct many months **one month at a time** and says not to wait for confirmation, continue automatically while preserving strict monthly isolation:

- process and report exactly one month per execution;
- keep an ordered durable ledger with `completed`, `pending`, and `current`;
- advance the ledger only after the selected month passes full independent readback and an idempotent `0 writes` rerun;
- on any blocker or failed gate, leave the ledger unchanged and retry the same month rather than skipping it;
- do not ask for confirmation between successful months, but deliver a separate result for each month;
- treat the re-read ledger—not scheduler run count, scheduler status, or a claimed successful delivery—as the authority for progress;
- serialize runs and provide retry capacity; once `pending` is empty, stop or pause recurring execution rather than emitting repeated completion messages.

See `references/sequential-multi-month-reconciliation.md` for the ledger schema, per-month publication gates, atomic advancement, and scheduler-safety rules.

## Yclients access setup

- Do not ask for passwords, cookies, or tokens in chat. Have the user place tokens in a local secret file with restrictive permissions, then use only read-only API calls.
- Marketplace application setup can require a **Webhook URL** before it allows saving API settings, even for a read-only reporting integration. Use a controlled HTTPS endpoint that acknowledges requests and does not persist payloads; do not point client-data webhooks at public third-party request bins.
- Connection/Marketplace fields such as public description, gallery, FAQ, registration redirect, and callback URL are normally irrelevant to a private read-only reporting integration unless the UI marks a field mandatory.
- If User Token auth returns an authorization error, determine from the current official Yclients documentation whether an app/partner token is additionally required; never guess token formats.
- Do not use the company-users endpoint as a generic API health check: it needs the distinct `Управлять пользователями` permission and can correctly return 403 for a read-only reporting app. Verify client-list/search and subscription endpoints instead.
- A Marketplace app has a separate system user. When access is expected but client endpoints fail, verify the application-to-branch connection status and that the app scopes were selected before treating the branch owner’s UI rights as the cause.

## Reconciliation semantics

- A subscription card’s **expiry date** is its “valid through” / “Срок действия” field, not its creation or activation date. Recompute expiry-dependent status and balance placement at apply time: if a positive balance has crossed its expiry date since the audit checkpoint, change the row to `Просрочен`, move the balance from `Осталось` to `Просрочилось`, and show current remaining as `-` in the same atomic update. Never combine a freshly computed status with a cached checkpoint `expired` flag. When proving mirrored same-day transfers, parse each dated history operation as a separate block; an unrelated later expiry-date operation must not supply the date for an earlier balance change.
- Count actual consumption from subscription **write-offs** in history, not only appointment statuses. Statuses such as waiting, attended, or confirmed can all coexist with a real consumption event depending on the business workflow.
- A manual subscription balance change by an administrator is **not** attendance and is **not** overdue. Report it separately in four columns in the main block only: `Уменьшили групп`, `Прибавили групп`, `Уменьшили инди`, `Прибавили инди`; do not add these columns to the lower `Пакет консультаций 3/5/8` block. Calculate each effective `Групп` / `Инди` quantity as the source quantity minus manual decreases plus manual increases, but never below `Отходили + Осталось + Просрочилось` for that type. This floor handles cases where the source has zero but the card lifecycle proves more consultations were actually consumed. Sum decreases and increases independently rather than only the net change. Calculate `Отходили` only from actual write-off events. Some exports already contain the post-adjustment quantity or an intermediate quantity after additions but before later decreases. Compare the exported value with: `current lifecycle = Отходили + Осталось + Просрочилось`; `reconstructed original = current lifecycle + decreases − increases`; `source − decreases`; and `source + increases`. If the export equals the current lifecycle or reconstructed original, do not apply the same balance change again. If `source − decreases == current lifecycle`, the source already includes the additions and only the later decreases should be recognized; if `source + increases == current lifecycle`, the source already includes the decreases. In every case, avoid applying either side of the manual sequence twice.
- When the user-approved vocabulary includes `Обнулен`, assign it only when every available consultation balance was manually reduced to zero and no active subscription remains; set `Групп` equal to `Отходили групп` and `Инди` equal to `Отходили инди` (or `0` when nothing was attended), preserve the manual-change columns as evidence, and color the entire row yellow. Implement the test **per available card family**, not as `all balances == 0 AND any decrease > 0`: an available group family must have a positive net decrease (`group_decreased > group_increased`), and an available individual family must have a positive net decrease (`ind_decreased > ind_increased`). For this test, treat a family as available only when its source quantity, attended/balance lifecycle, or manual operations are non-zero; a zero-balance placeholder card with zero source and no operations must neither block a genuine zeroing of the other family nor make an otherwise empty row `Обнулен`. Require at least one meaningful available family before assigning `Обнулен`. The net manual decrease does not need to equal the original purchased quantity: if write-offs consumed part of the family and a later balance-change operation explicitly reduced the remaining balance to zero, the row is still `Обнулен` (for example, 5 attended plus a final decrease of 1 from a 6-unit family). Preserve the exact zero-ending balance transition as evidence so this is distinguishable from an unrelated earlier decrease followed by natural exhaustion. A temporary decrease followed by an equal increase is net zero and must not make a naturally exhausted family `Обнулен`. Otherwise a naturally exhausted family plus an unrelated small or reversed manual decrease is falsely classified as `Обнулен`; keep such a row `Исчерпан` when all balances are zero. **Implementation gate:** classify the status first, then override the already calculated effective `Групп`/`Инди` values with the actual attended values when status is `Обнулен`; computing effective quantities before classification and returning them unchanged can leave source units in a yellow zeroed row. Require row-level equality `quantity = attended + remaining + overdue` for every `Обнулен` row after this override. If a verified exception is explicitly marked `Абонемента нет`, set every numeric consultation and manual-change field to `0` so it cannot affect totals, while preserving the red exception marking and explanatory note. Do **not** impose this equality globally on ordinary rows: under the approved source-minus-decreases-plus-increases rule, an effective purchased total may legitimately exceed the currently visible lifecycle, and `Нереализованные = effective total − attended − overdue` may therefore differ from `Осталось`.
- **Never calculate attendance only as `purchased − current balance`.** That fails whenever an administrator changes a balance. Before publishing a monthly sheet, audit **every matched card’s** detailed subscription history and the client visit history: actual `Списание` / use must reconcile to visits; `Изменение баланса` is excluded from attended and overdue, reported separately, and applied to the effective `Групп` / `Инди` quantity according to the approved net-adjustment rule. Do not claim a full audit if only card balances were read. For browser/UI audits, process checkpointed small batches, persist each client result before moving on, and reconnect/open a fresh authenticated tab if the UI automation session becomes unresponsive; never discard already verified rows. Before deciding that a client has no cards, enable `[data-locator=all_abonements_visibility]` / «Показать все абонементы и сертификаты, включая просроченные и исчерпанные» and wait for card containers to reload. A missing card before this toggle is not an audit result. When an unrelated prior/later card family is deliberately excluded from the requested sale, the client-wide visit history can still include visits from that excluded card; do not reattach it merely to force equality. Persist the excluded card locator/reason and allowlist the exact `(selected group write-offs, group visits, selected individual write-offs, individual visits)` tuple for that source row.
- Treat `0 write-offs = 0 visits` as confirmed only after a relevant group/individual card was positively selected and its detailed history panel loaded. Equality between two empty or failed extractions must remain an exception, not an automatic zero update. In browser audits, wait for each expanded history panel to contain dated operation rows before parsing; an immediate read after clicking can silently return empty history. Normalize whitespace in visit-history labels (for example match `Абонемент\s*1\s*визит` rather than a literal newline), because Yclients inserts tabs and variable line breaks. Extract card containers with the valid CSS selector `[data-locator^="abonement_container_"]`; do not use jQuery-only inequality syntax such as `[data-locator!=abonement_container]` with `document.querySelectorAll`, because it throws and can be mistaken for an empty card list.
- Inspect both group and individual cards even when the CSV has `0` for one type. A Yclients card can represent an additional real package absent from the export. **Never replace that zero with a hard-coded “standard” quantity.** Derive the effective quantity from the selected card’s lifecycle: actual write-offs plus current/expired remaining units, with every manual balance change explained separately. Positive balance additions can make more units available and consumed, but the `Изменение баланса` operation itself is never attendance or overdue. Require semantic card/course compatibility and inspect history when card dates or quantities disagree; nearest-date matching alone is insufficient. Card-title filters must have an all-card fallback: if no normally named card matches, inspect every visible card and its history because an individual consultation card can have an unexpected custom title. A card created/sold at the source-sale date with the correct lifecycle may be authoritative despite that title; only the exact title `Групповая консультация` is group. In particular, do not attach a card family with source quantity `0` merely because it is the nearest available card when it was created months after the source sale and its history begins with a separate later `Продажа`; treat it as a later purchase unless course semantics and lifecycle evidence tie it back to the requested sale. Apply the same evidence test to earlier cards: exclude an old family when its sale/usage belongs to another purchase, but retain a pre-existing card if a balance addition or validity-date change near the requested sale proves it was reused for the current row. Keep the relevant requested-month card family, exclude unrelated families, and leave an explanatory cell note.
- For this report, calculate individual consumption from the **sum** of actual subscription-use/write-off amounts in the detailed history: each whole `1 ₽` equals one individual consultation. Do not rely on fixed pairs—fragments can vary (`0.08 + 0.92`, `0.05 + 0.95`, etc.). Exclude every `Изменение баланса` and reconcile the resulting whole-consultation count against client visit history.
- The API’s `balance_container.links[].count` may be zero even when the visible subscription balance is non-zero; parse the visible `balance_string` such as `(x7)` first, then validate against history where available.
- Do **not** label a row `Нет абонемента` just because an active-subscriptions endpoint returned no result. First reconcile expired subscriptions through an endpoint/UI source that includes them.
- If the authenticated Yclients client card is available, its read-only UI request can provide the complete fallback: `GET /loyalty_cards/get_client_loyalty_cards_json/{salon_group_id}/{salon_id}/{client_id}/{full_phone}?show_all_statuses_abonements_certificates=1&show_redesign_view=false`. It returns JSON containing card HTML, including active, expired, and depleted subscriptions. Parse only the displayed card data; do not invoke edit/save controls. Close any temporary browser tunnel immediately after collecting data.
- Do not store a single client or report row per email in a dictionary: duplicate Yclients client cards can share email, and separate purchases can share the same person, phone, corrected email, or even contain a malformed email. Preserve one row per distinct purchase ID/source row. Build candidates from email, full normalized phone, and—when the sales export has no contact—an exact Telegram username embedded in the Yclients display name. Select the candidate and card lifecycle separately for each purchase using required card types, semantic course compatibility, and creation-date distance; retain unresolved ties for audit. Never silently drop a source row merely because its email lacks `@`. **Implementation gate:** carry a stable per-sale identity (source row or sale ID plus purchase date) through skeleton, checkpoints, reconciliation, notes, and final write. Before applying, assert that every source identity appears exactly once and that `main rows + package rows = source rows`; an email-keyed result dictionary is forbidden even when the current month happens to have unique emails.
- Treat a missing card type independently from a missing subscription row. If a group card is verified but no individual card exists in any status, keep the group values and set only individual fields to zero with a note (and vice versa). Reserve red `Абонемента нет` for a verified whole-row absence; do not erase a confirmed card family because its companion type is missing.
- When the agreed report vocabulary is `Активирован`, `Просрочен`, `Исчерпан`, plus the user-approved `Обнулен`, enforce it exactly. For an expired subscription, put its balance in overdue columns and show current remaining as `-`; for zero balance use `Исчерпан` unless the full manual-zeroing rule for `Обнулен` applies.
- If a CSV sale cannot be matched after exact email, normalized phone, exact Telegram username, and known alias checks, do not invent a technical status such as `Нет абонемента`. Keep it as an explicit exception. When the user requests visual marking, color the entire source row red and attach a cell note explaining which identifiers were searched and that no Yclients card was found; do not silently delete the sale or coerce its attendance to zero.
- Never publish a full-month attendance correction incrementally from exploratory UI batches. Save evidence/results per batch, verify a known-positive write-off parses non-zero, inspect the resulting monthly totals for plausibility, and only then apply a reversible/atomic sheet update. A near-zero total after a previously non-zero report requires root-cause investigation before writing.
- Overdue is normally the remaining subscription balance once its expiry date has passed or its Yclients state is expired. Include expired subscriptions in API/UI queries when reconciling.

## Client provisioning and subscription issuance

When the user asks to create clients, issue subscriptions, or make a named balance/contact correction, treat it as a separate staged write workflow:

1. **Apply scope changes immediately.** The latest user instruction is a hard execution boundary. If a bulk request is narrowed to one named client, cancel every pending bulk action, discard the earlier executable plan, and rebuild a one-client preflight. Never finish the earlier “safe subset” first.
2. Filter the sales source to explicit purchase-date/flow bounds, preserve one stable sale identity, and verify source freshness before touching YCLIENTS. Produce a read-only dry-run with exact planned counts and exceptions before bulk writes.
3. Normalize phone/email and search before creating. Require exact non-conflicting identity evidence under the active policy; missing contacts and partial phone/email conflicts are exceptions unless the user explicitly resolves a named conflict.
4. Keep the ordinary bulk policy strict: current automatic issuance may create an approved new card only for a new client or an exact existing client with proven zero subscription history. Do not weaken the global executor to satisfy a one-off correction.
5. Issue an abonement through its live-linked special inventory good: sale document → goods transaction → full-network card read-back → approved balance/period setters. **Never send an abonement type to `POST /api/v1/loyalty/cards/{company_id}`**; that endpoint is for loyalty-card types and has returned `Указан недопустимый тип карты` for abonements.
6. Implement an explicitly approved named exception as a separate allowlisted executor/ledger constrained to the exact client ID, card ID, type, delta/target, and requested contact field. Re-read all values immediately before write; do not generalize the exception into future bulk behavior.
7. Before updating an existing client, persist complete original `name`, `phone`, `email`, and `last_change_date`. Patch only the requested contact while sending the currently read required name/phone fields; read back the email and prove protected fields are unchanged. Check that the target email is unused by every other client.
8. For a named card correction, verify the exact card through the full-network endpoint one ID at a time and prove `card.goods_transaction_id → transaction.client_id`. Do not identify the target solely from a phone-level active-card list when exact card IDs exist. In code, compare normalized titles directly; never write `str(title == expected)` in a filter because both `"True"` and `"False"` are truthy strings.
9. Persist before every write and read back after every write. Recovery accepts only the saved before-state or exact target-state; any third value is a conflict. Re-run the executor and require zero writes, then independently verify every touched client/card and every explicitly excluded client.

## Named existing-client subscription additions

For a user command that names one existing client and requests a target family/quantity, use the scoped exception workflow rather than the ordinary bulk no-top-up policy: exact Telegram/email/phone identity, fresh all-status target-family check, separate handling of other active card families, live good/type linkage, final-balance readback, preserved default validity when no expiry is requested, narrow ledger, and a zero-write rerun. For an individual request, a group card is not evidence of an individual card: classify card families by the live card/type title and require the target family itself to be absent before `issue_new`. Validate subscription-type metadata with its direct `type.title` field (not a generic nested-card title helper), and expect that a standard individual good can issue with a default balance larger than the requested target; set the exact absolute target balance (for example `1`) only after proving the newly issued card’s transaction belongs to the exact client and good. Never rely on a network abonement list filtered only by `client_id`/`phone`; it can return an unfiltered page. Follow `references/client-provisioning-and-subscription-issuance.md` → **Named existing-client card issuance** and `references/named-individual-issuance.md`.

If the user explicitly changes the command to **«выдай новый» / «создай новую карточку»** after an existing card was found, treat that as an explicit scoped exception to the duplicate-skip gate—not as permission to top up or alter the existing card. Rebuild a separate allowlisted executor for the exact client, target good/type, quantity, and expiry; retain the existing card IDs in `before_card_ids`; select the newly created card by the before/after card-ID difference and prove its goods transaction ownership. Distinguish semantically different individual families by exact live title (for example, a PIM individual type versus the standard `Индивидуальная консультация` good), and do not merge their balances. Set the new card’s absolute balance and requested period independently, read back title/balance/expiry/transaction/document, then rerun the scoped executor with `0 writes`.
### User command semantics and interrupted-write recovery

- For this user's named YCLIENTS commands, **«спиши», «забери», and «уменьши» mean reduce the existing abonement balance**, not record attendance. Compute and persist `target_balance = verified_current_balance - requested_delta`; do not substitute a visit/write-off transaction.
- **Partial issuance recovery must be ledger-first.** If a run has already created the client, document, goods transaction, or card, do not restart the normal preflight: the newly created client will now correctly appear as an exact match and a duplicate/create gate may block recovery. Read the persisted `stage` and per-operation card/transaction IDs first, prove each side effect through `goods_transaction_id → exact client_id + good_id + title`, and resume only the missing balance/period/readback stages. Never call `issue_card` again for an operation whose transaction or card ID is already persisted. The recovery executor must bypass client-creation checks only for the immutable, exact allowlisted ledger state; it must still fail closed on missing ownership or unexpected IDs.
- **Never assume one universal default balance after issuance.** Standard individual and group abonement types can have different configured defaults (for example, individual 12 and group 14), while the requested source quantity can be 1/2/13/etc. Persist the observed post-issue balance, accept it only when it matches the live type's known default or the exact target, then set the absolute target balance and verify it. A balance mismatch must be handled by a type-specific recovery allowlist, not by reissuing the card or blindly applying a generic `if balance == 12` branch.
- Use the abonement endpoint `POST /api/v1/chain/{chain_id}/loyalty/abonements/{card_id}/set_balance` for this correction. The loyalty-card endpoint `/api/v1/company/{company_id}/loyalty/cards/{card_id}/manual_transaction` is a different resource and must not be retried with an abonement ID.
- Persist an immutable allowlist and before-state, re-read the exact card after the write, verify the target balance and unchanged expiry, then rerun the executor and require `0 writes`.
- For bulk active-card or history audits, use serial or low-concurrency pacing. Treat YCLIENTS `429` as a transient transport failure with capped backoff; if any client is rate-limited, never execute the resulting partial manifest—rebuild and verify the complete read-only manifest first.
- If an issuance command times out after persisting an `issuing` stage, treat the side effect as unknown: do not reissue. Inspect the ledger and full-network card history, prove any newly created card through its goods transaction → exact client ID/good ID, then recover only the missing balance setter on that card. Record the recovery as a separate verified stage.
- When the client search exposes only a masked phone, never invent a full number. Bind the write to the exact client ID/email and exact card/transaction evidence; use a normalized masked value only when a live read has already proven it resolves to that exact client.

See `references/named-client-balance-correction-recovery.md` for the endpoint distinction, manifest fields, timeout-recovery recipe, and masked-phone handling.

## Database-backed package issuance and delayed card recovery

When a user asks to issue a client's subscription “from the database” and the exact email is absent from the YCLIENTS client list:

1. Query the authorized FF sales API for the exact normalized email across the required purchase window (not only local exports). Require exactly one sale and preserve its `purchaseID`/sale reference.
2. Derive the target from the mapping, never from a guessed default: `Пакет консультаций 3/5/8` maps to `Консультации (3/5/8 шт.)`, with the mapped package good ID and fixed package quantity. Package validity is the live YCLIENTS type's configured period; do not apply a missing or expired `gracePeriodEndDate` to package cards.
3. If the source sale supplies complete name, Telegram username, phone, and email and no exact YCLIENTS match exists by normalized phone/email, create the client using the proven `POST /api/v1/clients/{company_id}` flow, read it back, and verify all three contact fields before issuing. Do not create a client merely because a subscription search returned no card.
4. Verify the package good title and `loyalty_abonement_type_id` against the unique live subscription type before any write. Issue the special good, then set the package balance to the mapped quantity if the created card's default balance differs.
5. Derive card-list date bounds at runtime and make the upper bound safely exclusive of the current day. Never use a stale hard-coded cutoff: a transaction created after that cutoff can be real while the card is absent from the scan.
6. Persist the ledger before client creation and before sale issuance. If issuance created a client/document/transaction but card discovery failed, treat the side effect as unknown: read the ledger, verify the goods transaction's exact `client_id` and `good_id`, widen the card-read window, find the card by `goods_transaction_id`, and recover only the missing balance setter/readback. Never reissue.
7. Require a final card proof through `card.goods_transaction_id → goods transaction → exact client ID/good ID`, then rerun the executor and require `0 writes`. Report client creation separately from subscription writes.

For masked-phone clients, do not invent a full number. Prefer exact card IDs and transaction ownership; a goods transaction readback may contain the authoritative unmasked client contact, but it is evidence for verification, not a reason to overwrite source data. ## Fresh-window overrides and partial-issuance recovery

For recent-window bulk issuance, normalize the selected source emails first and filter the override map to emails actually present in that immutable source snapshot before calling any helper that rejects absent override keys. Use the same filtered override set for dry-run, apply, independent verification, and the ledger; report historical overrides absent from the selected window separately instead of treating them as a source error. When a wrapper invokes the builder and mass executor in one process, fetch the FF source exactly once and inject the same snapshot into both stages; a mutable API can change one row between sequential reads and create a false missing-override/reference mismatch. Normalize override email keys before passing raw dictionaries to helpers, because CLI parsing may normalize keys while direct dict lookup remains case-sensitive. Re-read the source before apply and stop if source count or sale identities drift.

If a mass ledger operation is left at `stage=issuing` with `issue_meta.stage=document_created` but no `goods_transaction_id`, treat the side effect as unknown and never blindly reissue. Read the exact saved document ID (a cleanup-confirmed 404 proves the empty document was removed), query the exact client’s active/all-status target family by source phone, and search the saved transaction/card ownership evidence. Only when the document is gone and no target card or goods transaction exists may the single failed operation key be reset for one retry; preserve every completed operation and client checkpoint. If a card or transaction exists, recover that card by exact transaction → client/good ownership instead of issuing again. After recovery, independently verify every card’s exact title, balance, expiry, card ID, transaction, document, client ownership, and good/type linkage; clear only resolved failure entries, then rerun the identical executor and require zero writes.

For independent ledger verification, read `good_id` and `document_id` from each operation’s saved `issue_meta` when the ledger stores them there; do not assume they are duplicated at the operation’s top level. Report both the number of newly issued cards in the current run and any pre-existing completed operation keys separately.

### Immutable operation-manifest and completeness gates

- Persist the initial approved `(sale_ref, target type)` operation-key set and its cardinality before the first write. Never let a recovery run recompute a smaller success denominator solely from the mutable ledger plus a refreshed planner: after a partial issue, the planner may reclassify the sale while a failed companion type disappears from both `ready` and the ledger.
- A verifier that reports “all ledger rows valid” is insufficient unless it also proves `approved operation keys == completed operation keys == independently verified card keys`. Reconcile source-plan coverage per family so an individual success cannot hide a missing group card, or vice versa.
- If a failed `issuing` operation has no transaction, its cleanup document is confirmed gone, and no target card exists, retain the operation key and recovery evidence while marking it retryable; do not delete the key. If the current executor cannot preserve that invariant, recover with a separate exact-client/type scoped ledger rather than shrinking the original period ledger.

For wrapper scripts, direct `apply_telegram_overrides()` calls must receive normalized email keys. CLI parsing may lowercase keys while a raw dictionary remains case-sensitive, so an uppercase source email can pass the builder and fail the executor. Fetch one immutable FF snapshot per wrapper invocation, filter overrides to normalized emails present in that snapshot, and pass the same snapshot/map to builder and executor. The apply invocation must still fetch fresh, rebuild/validate before writes, and reject sale-identity drift.

## Recent purchase-date bulk windows

For a request such as «за последние N недель», read the actual current system date and convert it to an inclusive calendar interval: `start = today - (7*N - 1) days`, `end = today` (for 3 weeks, 21 dates: `today - 20 days` through `today`). For «за последние N дней», use the same inclusive rule: `start = today - (N - 1) days`, `end = today`; a 10-day window therefore spans today and the previous 9 calendar dates. Filter by `userCourse.purchaseDate`, not course start/activation date; send the FF API upper bound as exclusive `end + 1 day`, then assert every returned purchase date and `purchaseID` is inside the requested set and purchase IDs are unique. Use a separate period ledger named from the exact start/end so a new window cannot overwrite a previous run. Run a read-only dry-run before writes and report source rows, unique sales, new clients, ready operations, already-completed keys, exceptions, and planned top-ups; require `planned_topups == 0` and reject every action other than `issue_new` for this bulk policy. Existing/completed `(purchaseID, target type)` keys are skipped from cumulative ledgers, while named existing-client exceptions must use the scoped workflow rather than silently becoming bulk top-ups. If a user supplies exact Telegram overrides, bind and apply only overrides whose normalized email is present in the selected source window; historical overrides for emails absent from this window must not abort the run or be applied to unrelated rows. If a blank source `tgUsername` is resolved by an approved override, apply the override to the in-memory source sale before calling any source-client builder/provisioning helper; those helpers may reject an otherwise complete sale as incomplete contacts when the override is applied only afterward. If the user adds one named override after a period has already been applied and the refreshed period contains other ready sales, do not rerun the whole apply blindly: filter to that exact sale/email and use a scoped executor, leaving unrelated ready sales untouched. Recover the ID only from a known exact package card: read the card by one `abonements_ids` value, follow `goods_transaction_id` to the goods transaction, then validate the good title and `loyalty_abonement_type_id` against the live abonement type. Add a regression assertion before retrying. List unresolved emails with concrete missing fields/reasons, then rerun the identical period executor and require `0 writes`.
